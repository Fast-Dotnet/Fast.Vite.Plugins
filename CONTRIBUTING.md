# Contributing to fast-vite-plugins

Thank you for helping improve `fast-vite-plugins`. This guide describes the development and review requirements for changes to the repository.

## Before you start

- Search the [existing issues](https://gitee.com/FastDotnet/fast.vite.plugins/issues) before opening a new one.
- Discuss substantial features or breaking changes in an issue before implementation.
- Report suspected vulnerabilities privately as described in the [security policy](./SECURITY.md), not in a public issue.

## Development setup

The supported development environments are Node.js `^22.18.0 || ^24.18.0` and pnpm `^11.0.0`.

```bash
git clone https://gitee.com/FastDotnet/Fast.Vite.Plugins.git
cd Fast.Vite.Plugins
corepack enable
pnpm install --frozen-lockfile
pnpm check
```

Create a focused branch from the latest `master` branch before making changes:

```bash
git switch master
git pull --ff-only origin master
git switch -c feat/short-topic
```

Use `pnpm dev` when you need a watch build. Do not edit `dist/` manually; it is generated by `pnpm build` and is not committed.

## Making changes

- Keep each change focused and follow the existing TypeScript, naming, and plugin patterns.
- Implement the current API directly; keep callers, tests, and documentation in sync instead of adding old-version shims.
- Avoid adding runtime dependencies unless the change cannot reasonably be implemented without one. Vite is currently the package's only peer dependency.
- Add or update tests for changed behavior, regressions, public types, package exports, and integration behavior as applicable.
- Keep public API TSDoc, both README files, [api.en](https://docs.fastdotnet.cn/en-US/frontend/vite-plugins/api/), [api](https://docs.fastdotnet.cn/zh-CN/frontend/vite-plugins/api/), and `CHANGELOG.md` synchronized with user-visible API or behavior changes.
- Preserve output-path validation, deterministic generation, watcher cleanup, and explicit diagnostics when working on file-system or generator features.
- Never include credentials, tokens, private data, or generated build artifacts in a commit.

The repository root is the public npm package. Changes to exports or packaging must continue to produce an ESM-only archive with declarations and only the files required by the package contract.

## Validation

Run the full quality gate before submitting a change:

```bash
pnpm check
git diff --check
```

`pnpm check` performs type checking, linting, formatting checks, builds, runtime tests, a real Vite integration test, public API type tests, and package-contract tests.

For package-layout or export changes, also inspect the publish archive:

```bash
pnpm --config.ignore-scripts=true pack --dry-run
```

Do not remove or weaken tests, type checks, lint rules, or assertions to make validation pass.

## Submitting a change

Before opening a pull request:

1. Rebase or update your branch against the latest `master` without introducing unrelated changes.
2. Review the complete diff and remove debugging code and generated files.
3. Confirm that the required validation commands pass.
4. Describe the problem, the chosen solution, compatibility impact, and validation performed.
5. Link the related issue and call out any breaking change, security consideration, or follow-up work explicitly.

Keep commits clear and scoped to the change. Maintainers may request revisions when behavior, tests, documentation, compatibility, or package contents are incomplete.

## Release and deployment

Contributors should not publish packages or create release tags. Maintainers follow the repository's [development, release, and deployment guide](./docs/DEVELOPMENT_RELEASE_DEPLOY.zh-CN.md) after a change is accepted.
